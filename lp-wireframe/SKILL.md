# Landing Page Wireframing

Build a design foundation that lets a visitor recognize the offer, understand how it works, judge the evidence and commitment, and take the appropriate next step. Deliver a wireframe the designer can review at actual reading widths, with enough detail to make layout and interaction decisions before visual polish.

## 1. Establish the decision

Read the supplied copy and brief. Identify the visitor, what brought them here, what the entry message promised, the main unresolved doubt, the commitment, and the immediate result of the primary action. Use observed buyer behavior or research when available. Treat inferred doubts as hypotheses.

Use the actual headline, terms, proof, CTA and form labels. Treat explicitly approved wording, claims and terms as fixed. If order is also fixed, preserve it and flag any consequential issue. Resolve conflicting inputs against the latest authoritative source. If a material conflict remains, surface it in the handoff and mark the affected frame provisional. Ask only when an unresolved detail changes the layout or action enough to prevent useful progress. Label a gap in the frame only when reviewing the layout or action depends on seeing where that detail belongs. Record other gaps that matter in the handoff. Use a layout change first when wording wraps awkwardly. Put proposed copy edits in the handoff.

## 2. Lay out the argument

Map each material visitor doubt to the supplied answer and the evidence it needs. Sequence sections by the decisions visitors must make. A warm, high-intent visitor may need offer, fit and action early. A visitor from unfamiliar outreach may first need the mechanism or a relevant result. Place the strongest remaining doubt before the commitment it affects. Combine repeated answers where the approved structure permits. Give each section a question it resolves and a reason to appear where it does.

Use the first mobile viewport to make the audience, offer and relevance recognizable and to make the next step easy to locate. Check the actual crop of the real copy. Keep a hero visual only if it explains something faster or makes evidence easier to interpret. Specify what should draw the eye first, second and third in the hero and other high-stakes sections. Use scale, position, weight and spacing to establish that order in grayscale.

Choose the form that reflects the relationship in the copy. Use steps for a sequence, aligned rows or a table for shared attributes, and a list for independent criteria. Use equal cards when the items deserve equal emphasis. Keep metric, label, source and material caveat in one group. Check heading and button labels in isolation, then check line length and wrapping with real copy.

Read [decision-patterns.md](references/decision-patterns.md) when a major layout choice has competing approaches, the available proof is limited, or added persuasion, disclosure, or a complex action needs a concrete design rule. Compare two rough sketches of the same decision only when the choice could materially change comprehension or action. Keep the proposition and evidence constant so the comparison tests placement or hierarchy.

## 3. Show the entire action

Use a recognizable primary-action treatment and consistent labels for repeated instances of the same action. Place relevant terms, separate costs, eligibility and responsibilities before the commitment. Show what the click starts beside the control when the label leaves room for doubt. Give each proposed form field a purpose in qualification, routing, or follow-up. Specify visible labels, optionality and help where needed. Put additional detail behind a disclosure only when the buyer can decide without it.

Trace the actual journey from the CTA through applicable input, pending, validation, service failure, success and follow-on states. Show what persists on retry, where focus moves, and the next action in each relevant state. Distinguish submission from booking and booking from payment when they are separate. Label simulated outcomes and unresolved integrations in the review artifact. Keep prototypes local and inert against real systems unless the user explicitly asks for a connected implementation.

## 4. Deliver the wireframe

- **Full page.** Default to one content-complete, responsive, low-to-mid-fidelity wireframe with restrained styling. Use the user's requested format or existing design surface. Otherwise, make a self-contained HTML preview when file generation is available. Show desktop and mobile arrangements in the same preview or as paired frames. Put visitor-facing content inside the wireframe and keep reviewer notes out of its reading path.
- **Focused change.** Show the requested section and the neighboring context needed to judge it, with mobile behavior and affected action states. A compact rendered frame is sufficient when the interaction can be understood from it.
- **Audit.** Tie each material issue to a location, evidence in the current wireframe, the visitor task affected, and a specific structural fix. Redraw the affected section when requested or when a verbal fix leaves the structure ambiguous.

In the handoff annotate meaningful sections with **visitor question · content and proof · layout choice · how to check it**. Record consequential source gaps and the actual CTA destination and states. Keep layout decisions clear enough to build from, including mobile order, grouping and behavior at the width where components change.

## 5. Verify and refine

Inspect the actual output at representative widths for the requested scope. For a full page, include mobile and desktop. For a rendered web prototype with a mobile layout, also check narrow reflow near 320 CSS px. Check hero crop, real line breaks, visual focus, section order and group integrity when stacked. Read headings and action labels alone. Verify the source and visual reading order agree where order matters. Check semantic headings, keyboard access, visible focus, meaningful control names, error cues that do not depend on color, usable tap targets and legible contrast. Check keyboard or sticky-element overlap when relevant. Trace or exercise the CTA and its states. Fix material problems and repeat affected checks.

Use three short, neutral buyer tasks to check understanding, evidence or fit, and action. Ask visitors what they think will happen before they click, then compare their expectation with the next state. Label an internal walkthrough as a walkthrough. Report genuine buyer observations only when observed, and conversion effects only when measured with real traffic. Name the strongest unresolved design decision or verification gap in the handoff.
